## 生产级架构设计报告（纠正上一版判断）

- 输出文档：`docs/生产级架构设计报告.md`
- **关键认识转变**：生产级 ≠ 减少微服务。上一版从课程项目角度建议"合并 inventory/cart/search 到 product"，但从生产级角度重新分析后发现这个判断是错误的。
- **生产级架构核心原则**：
  1. inventory 必须独立 —— 它是整个系统的瓶颈点，秒杀时需要独立扩容 10 倍，product 不需要。库存和商品是两个完全不同的限界上下文（强一致 vs 最终一致、Redis-first vs MySQL-first、秒杀独立扩容 vs 普通扩容）
  2. cart 必须独立 —— CQRS 模式（写时从 product 拉快照存 Redis，读时本地完成）完美解决跨服务查询。购物车是 Redis-first，与 product 的 MySQL 范式完全不同
  3. search 必须独立 —— ES 集群独立管理，搜索流量是商品详情的 5~10 倍，需要独立的索引管道和扩容策略
  4. recommend 可以 P2 —— 初期 Redis ZSet 热度推荐放入 product，ML 化后拆出独立服务（可能是 Python）
- **最终裁定**：10 个运行时单元（1 网关 + 9 业务服务 + 1 个 P2 演进项）
- **报告覆盖 14 个章节**：
  - DDD 限界上下文逐服务分析（每个服务都有独立业务价值论证）
  - 完整的同步/异步通信矩阵 + CQRS 购物车方案 + Saga 编排方案
  - Database per Service 策略 + 5 种数据一致性方案
  - 分布式事务设计（Saga 编排 + 补偿机制 + 本地消息表）
  - 五层安全防护 + 服务间 HMAC 签名
  - 三维可观测性（Logs/Metrics/Traces）+ 告警规则

  - 整合 Doc1+Doc2 后的 3 阶段 10 周实施路线图

## 服务设计详细报告（11 个服务完整设计）

- 输出文档：`docs/服务设计详细报告.md`
- **服务总数**：11 个（1 网关 + 10 业务服务），含从 merchant 拆分出的 settlement-service
- **设计驱动**：用户两次追问引发深度讨论——①为什么商家部分只有一个服务？→ 拆出 settlement-service（金融数据隔离+批处理资源隔离）②商品/商家/admin 三者关系？→ 明确 admin 为严格 BFF，审核流程归属业务服务
- **每个服务细化到**：基本信息、按模块分组的完整功能清单、每个 API 的详细说明、数据模型、事件发布/消费清单、内部 Feign 接口、依赖关系、技术深度点
- **核心设计决策**：
  - merchant 拆为 merchant（入驻/审核/店铺）+ settlement（结算/财务/定时任务），安全级别 + 运行时特征完全不同
  - admin-service 严格 BFF：只做 UI 代理和只读聚合，禁止编排多步骤审核流程、禁止持有数据库
  - product/merchant/admin 三者解耦：审核流程在业务服务内部闭环，状态联动通过 MQ 事件驱动
  - cart CQRS：写时 Feign 拉快照，读时纯 Redis 零跨服务调用
  - inventory Redis Lua 原子扣减，秒杀独立扩容
  - search ES 独立集群，MQ 异步同步索引
- **完整输出**：13 个章节，含 21 个 MQ 事件总表、Feign+MQ 依赖矩阵、7 个典型场景链路深度分析
