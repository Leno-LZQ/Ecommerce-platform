## 零、核心理念：把"生产级"和"部署到哪"拆开

### 0.1 一个最常见的误解

```
很多人以为：
  生产级软件 = 部署在云服务器上 + 多副本 + 高可用集群

实际情况：
  部署目标是"在哪跑"，生产级是"怎么写的"
  → 这两件事完全独立
```

### 0.2 本方案的定义

```
                    ┌─────────────────────────────┐
                    │     生产级软件工程            │
                    │  ✅ 代码质量规范               │
                    │  ✅ 单元测试 ≥80%              │
                    │  ✅ 集成测试 + 契约测试 + E2E   │
                    │  ✅ CI/CD 自动化流水线          │
                    │  ✅ SonarQube 质量门禁          │
                    │  ✅ 安全审计 (SAST + 依赖扫描)   │
           ┌─────── │  ✅ 结构化日志 + 监控 + 告警    │───────┐
           │        │  ✅ 限流熔断 + 降级策略         │        │
           │        │  ✅ 数据库备份 + 恢复演练        │        │
           │        │  ✅ Git Flow + Code Review     │        │
           │        └─────────────────────────────┘        │
           │                                               │
    ┌──────▼──────┐                               ┌────────▼────────┐
    │  部署目标 A  │                               │   部署目标 B     │
    │  本地 Docker │  ← 当前方案                    │   云服务器       │
    │  成本: ¥0   │                               │   Docker        │
    │  随时可用    │                               │   成本: ¥195    │
    └─────────────┘                               └─────────────────┘

    两个部署目标之间，只差一条 docker compose 命令 + 环境变量切换
```

### 0.3 这意味着什么

| 你得到的是 | 你没有的是（也不需要） |
|:----------|:---------------------|
| 代码经得起 Code Review | 7×24 小时在线 |
| 每次 push 自动跑全部测试 | 公网域名 + HTTPS |
| 安全漏洞在 CI 阶段就被拦截 | 多副本高可用 |
| 任何崩溃都能在 30 秒内自动恢复 | CDN 加速 |
| 监控面板能实时看到所有指标 | 异地灾备 |
| 一键就能部署到任何 Docker 环境 | 支付正式商户号 |

> **一句话**：代码质量、测试、安全、监控——这些都跟部署在哪没关系。本地跑照样能做。将来想上云，改一下 docker-compose 里的 `SPRING_PROFILES_ACTIVE=prod` 就行。

## 二、技术可行性全面分析

### 2.1 核心问题

> **在本地开发机上跑全套生产级工程实践，技术上可行吗？**

逐项回答：

### 2.2 内存可行性

```
本地 Docker 全量方案内存占用（16GB 开发机）：

组件             容器数   内存限制      实际占用     说明
──────────────────────────────────────────────────────
MySQL 8.0          1      768 MB       ~500 MB    数据少时更低
Redis 7.2          1      384 MB       ~150 MB    AOF 持久化
RabbitMQ 3.13      1      384 MB       ~200 MB    
Nacos 2.x          1      512 MB       ~350 MB    
Nginx              1      256 MB       ~50 MB     
gateway            1      384 MB       ~280 MB    
user-service       1      384 MB       ~280 MB    
product-service    1      384 MB       ~280 MB    
order-service      1      384 MB       ~280 MB    
payment-service    1      384 MB       ~280 MB    
cart-service       1      256 MB       ~150 MB    
inventory-service  1      256 MB       ~150 MB    
admin-service      1      256 MB       ~150 MB    
frontend           1      128 MB       ~30 MB     
Elasticsearch      1      768 MB       ~500 MB    可关闭
Logstash           1      384 MB       ~200 MB    可关闭
Kibana             1      256 MB       ~150 MB    可关闭
Prometheus         1      256 MB       ~150 MB    可关闭
Grafana            1      192 MB       ~80 MB     可关闭
SkyWalking OAP     1      可选          ~500 MB   可关闭
──────────────────────────────────────────────────────
全量（含可观测性）                     ≈ 4.5 GB    
纯业务（不含可观测性）                  ≈ 2.8 GB    
极简（仅核心中间件 + 5 个必须服务）      ≈ 1.8 GB    
```

> **结论**：16GB 开发机轻松跑全量。即使 8GB 机器，关闭可观测性组件（开发时也不需要 7×24 采集）也能流畅运行。日常开发推荐只启动 MySQL + Redis + 当前在写的那个微服务（用时 < 1GB）。

### 2.3 开发效率可行性

常见顾虑："全套可观测性跑在本地是不是很慢？"

```
组件启动耗时：
─────────────────────────
MySQL           : 10~15s
Redis           : 3s
RabbitMQ        : 10s
Nacos           : 20s
Nginx           : 2s
1 个微服务       : 5~8s (Spring Boot 启动)
ES + Logstash   : 30s (开发时按需启动)
─────────────────────────
docker compose up -d 全量启动 ≈ 60~90s
开发模式下只启动需要的 ≈ 20~30s
```

> IDE 热重载 + Docker 后台运行中间件，开发体验和纯本地开发几乎无差别。

### 2.4 CI/CD 可行性

GitHub Actions 运行在云端，不占用本地资源。本地只需要能 `git push`：

```
你的电脑                            GitHub 云端
─────────                          ──────────
git push  ─────────────────────→   Checkstyle 检查
                                   SpotBugs 扫描
                                   Unit Test
                                   Integration Test
                                   SonarQube 扫描
                                   OWASP 安全扫描
                                   ↑ 全程不占用本地 CPU/内存
←── PR 评论(通过/拦截) ────────────
```

> CI 完全在云端跑，本地零负担。免费额度（2000 分钟/月）对个人项目绰绰有余。

### 2.5 存储可行性

```
本地运行 6 个月后的磁盘占用：
─────────────────────────
Docker 镜像（构建缓存）      : 5~10 GB
MySQL 数据（测试数据）       : 100~500 MB
Redis AOF                   : 50~100 MB
ES 索引（保留 7 天）         : 500 MB ~ 2 GB
应用日志（7 天滚动）         : 200~500 MB
Prometheus TSDB            : 1~3 GB
─────────────────────────
总计 ≈ 7~16 GB
```

> 日常 `docker system prune` 清理无用镜像和构建缓存，可控制在 10GB 以内。

### 2.6 支付沙箱可行性

支付宝/微信支付沙箱环境支持本地开发：

```
沙箱回调方案：
─────────────
问题：支付平台需要回调你的服务器（公网 URL），本地 localhost 不可达

解决方案：ngrok 免费隧道
  ngrok http 8080
  → 生成公网 URL: https://abc123.ngrok.io
  → 在支付宝沙箱配置回调 URL 为 https://abc123.ngrok.io/api/payment/notify/alipay
  → 支付完成后，支付宝回调 → ngrok → 你的本地服务 ✅

或者更简单：
  沙箱环境通常也支持主动查询模式（不依赖回调）
  本地测试时用定时查询替代回调
```

### 2.7 各领域可行性汇总

| 领域 | 本地可行？ | 说明 |
|:-----|:--------:|:-----|
| **单元测试** | ✅ | JUnit 5，秒级运行 |
| **集成测试** | ✅ | Testcontainers 自动启动 Docker 容器 |
| **契约测试** | ✅ | Spring Cloud Contract，CI 中运行 |
| **E2E 测试** | ✅ | Cypress/Playwright，本地浏览器 |
| **Checkstyle** | ✅ | Gradle 插件，秒级 |
| **SpotBugs** | ✅ | Gradle 插件，秒级 |
| **SonarQube** | ✅ | 本地 Docker 启动 SonarQube，或 CI 中运行 |
| **OWASP 依赖扫描** | ✅ | CI 中运行，不影响本地 |
| **JWT(RS256)** | ✅ | 纯代码实现 |
| **RBAC 权限** | ✅ | 纯代码实现 |
| **API 限流** | ✅ | Nginx + Gateway，本地能测 |
| **ELK 日志** | ✅ | Docker Compose 本地启动 |
| **Prometheus 监控** | ✅ | Docker Compose 本地启动 |
| **Grafana 看板** | ✅ | Docker Compose 本地启动 |
| **SkyWalking** | ✅ | Docker Compose 本地启动（可选） |
| **CI/CD** | ✅ | GitHub Actions 云端运行 |
| **数据库备份脚本** | ✅ | 本地 crontab 或手动执行 |
| **支付沙箱** | ✅ | + ngrok 或主动查询模式 |
| **蓝绿部署** | ⚠️ | 本地可行但意义不大（开发阶段用不到） |

| **CDN** | ⚠️ | 本地不需要 |

> **最终结论**：23 项生产级实践中，**18 项在本地完全可行**，3 项半可行（支付沙箱、蓝绿部署、HTTPS），2 项不适用（CDN、7×24 在线）。不适用的是部署层面的差异，不影响代码的工程品质。

## 六、安全加固

> 安全加固**完全在代码层面**，跟部署到哪无关。JWT 签名、RBAC 权限、输入校验——这些代码写好了就是写好了。

### 6.1 认证升级

| 项目 | 课程级 | 生产级 | 本地跑有关系吗？ |
|:-----|:------|:------|:--------------:|
| **签名算法** | HS256 | RS256（非对称） | ❌ 无关 |
| **Access Token** | 30min | 15min + 轮换 | ❌ 无关 |
| **Refresh Token** | 无轮换 | 每次刷新旧 Token 失效 | ❌ 无关 |
| **权限** | 简单 RBAC | RBAC + 数据权限 | ❌ 无关 |
| **登录方式** | 用户名+密码 | + 手机验证码 + 第三方 | ❌ 无关 |

### 6.2 API 安全

| 措施 | 实现 | 本地跑需要吗？ |
|:-----|:-----|:------------:|
| **请求限流** | Nginx `limit_req` + Gateway `RequestRateLimiter` | ⚠️ 本地自用不需要，但代码写了就能用 |
| **防重放** | nonce + timestamp + Redis 去重 | ⚠️ 同上 |
| **防爬虫** | 滑块验证码 | ❌ 本地不需要 |
| **接口签名** | 支付回调验签 | ✅ 支付沙箱需要 |
| **CORS** | Gateway 白名单 | ✅ 前后端分离需要 |
| **SQL 注入** | MyBatis `#{}` | ✅ 任何时候都需要 |
| **XSS** | 输入过滤 + 输出编码 | ✅ 任何时候都需要 |

### 6.3 数据安全

| 数据 | 保护 |
|:-----|:-----|
| **密码** | BCrypt(cost=12) |
| **手机号** | AES-256 加密 + 日志脱敏 `138****8888` |

```java
// 这些代码写完，本地能验证，上云直接生效
@RestController
public class SeckillController {

    @GetMapping("/api/seckill/{productId}")
    @SentinelResource(
        value = "seckill",
        blockHandler = "seckillBlockHandler",       // 限流降级

    )
    public Result<?> seckill(@PathVariable Long productId) {
        // Redis Lua 原子扣减
    }

    // 限流后的降级响应
    public Result<?> seckillBlockHandler(Long productId, BlockException ex) {
        return Result.error(ErrorCode.TOO_MANY_REQUESTS, "活动太火爆，请稍后重试");
    }

    // 异常时的降级响应

    }
}
```

### 10.1 CI 流水线（每次 push / PR）

```yaml
# .github/workflows/ci.yml
name: CI

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

jobs:
  quality:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { java-version: '21', distribution: 'temurin' }

      - name: Checkstyle
        run: ./gradlew checkstyleMain -PCI=true

      - name: SpotBugs
        run: ./gradlew spotbugsMain

      - name: Unit Test + Coverage
        run: ./gradlew test jacocoTestReport

      - name: SonarQube Scan
        env:
```

## 十六、风险与应对

| 风险 | 应对 |
|:-----|:-----|
| **本地调试多服务麻烦** | Docker Compose profiles：只启动当前在写的服务，调哪个启动哪个 |

| **功能越做越多** | P0 > P1 > P2 严格优先级，每个 Phase 锁范围 |
| **代码写得像课程项目** | Checkstyle + SpotBugs + Code Review 三重保险 |
