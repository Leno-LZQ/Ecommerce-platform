## 二、对原有优化建议逐条分析

### 2.1 需求层面（业务闭环）

#### 建议 1：多规格商品（SKU）属性设计

> 商品-SPU + 库存-SKU 双表设计，Redis Key 设计为 `product:sku:{skuId}`

| 评估维度 | 结论 |
|:---------|:-----|
| **是否合理** | ✅ **非常合理且必要** |
| **文档是否已覆盖** | ✅ 已覆盖。DB 设计中已包含 `product_sku` 表（含 version 乐观锁、attrs 属性字段）；Lua 脚本 Key 设计为 `stock:sku:{skuId}` |
| **实施优先级** | P0（必须在开工前确定） |
| **风险** | 如果产品只有单规格（无 SKU），整个库存扣减、缓存设计都会局限于"玩具"场景；答辩时无法展示 SKU 级别的细粒度并发控制 |

**补充细化**：
- SKU 的 `attrs` 字段建议用 **JSON 格式**而非逗号拼接：`{"颜色":"黑色","容量":"128G"}`，方便前端解析
- 商品表 `product` 仍保留 `price` / `stock` 作为**默认值快照**（单规格时直接引用），避免无 SKU 场景下的空指针
- 布隆过滤器和缓存 Key 应当**同时存储 productId 和 skuId**：`bloom:products`（商品级）、`bloom:skus`（SKU级）

---

#### 建议 2：库存"预占"与"实扣"分离

> 下单→预占库存（冻结）；支付成功→实扣库存；超时取消→释放冻结

| 评估维度 | 结论 |
|:---------|:-----|
| **是否合理** | ✅ **非常合理，这是高并发库存系统的核心设计** |
| **文档是否已覆盖** | ⚠️ 半覆盖。文档有订单状态机 + 延迟队列取消订单 + 库存扣减 Lua 脚本，但**"预占"和"实扣"概念没有显式区分**。当前实现是下单直接扣库存，取消时才回滚 |
| **实施优先级** | P0 |
| **风险** | 当前"直接扣+回滚"模式在高并发下有两个问题：(1) 大量下单又取消导致频繁回滚；(2) 秒杀场景大量用户持有库存但不支付 |

**建议细化方案**：

```
Redis 库存结构：
  stock:sku:{skuId}:total    → 总库存
  stock:sku:{skuId}:frozen   → 冻结库存（已下单未支付）
  stock:sku:{skuId}:available → 可用库存 (= total - frozen)

Lua 预占脚本：
  1. GET available, frozen
  2. if available < quantity → return 失败
  3. DECRBY available, quantity
  4. INCRBY frozen, quantity
  5. return 成功

支付成功 → Lua 脚本：DECRBY total, DECRBY frozen
超时取消 → Lua 脚本：INCRBY available, DECRBY frozen
```

这样"预占/实扣"成为**独立的两个原子操作**，比当前"扣减→回滚"模式在语义上更清晰，答辩时也更有说服力。

---

#### 建议 3：售后逆向流程（退款退货）

> 申请退款 → 审核 → 库存回滚 → 资金退回

| 评估维度 | 结论 |
|:---------|:-----|
| **是否合理** | ✅ 合理，但复杂度较高 |
| **文档是否已覆盖** | ⚠️ 部分覆盖。订单状态机含 `REFUNDED(6)` 状态，支付表含"已退款"状态，但**没有实际退款流程接口** |
| **实施优先级** | P1（核心链路完成后追加） |
| **风险** | 退款涉及资金安全，对于课程项目来说即使只做"模拟退款"也需考虑：退款幂等性、库存回滚一致性、退款金额校验 |

**建议**：在支付模块中追加一个 **简单的退款接口** `POST /api/payments/{payNo}/refund`，流程为：校验订单状态→更新支付流水→更新订单状态→MQ 异步回滚库存。即使不接入真实支付退款 API，这个 **"逆向流程设计"** 本身就是答辩中的亮点。

### 2.2 技术深度层面

#### 建议 4：缓存穿透加"空值缓存"双保险

> 布隆过滤器误判时，缓存一个空对象（短过期时间）

| 评估维度 | 结论 |
|:---------|:-----|
| **是否合理** | ✅ **合理** |
| **文档是否已覆盖** | ✅ **已覆盖**。`ProductCacheService.java` 第 250 行缓存空值 30 秒 |
| **实施优先级** | 已实现（文档层面），核对代码实现即可 |
| **点评** | 原文档方案已经很完备：布隆过滤器（前置拦截）→ 空值缓存（兜底）→ 互斥锁（防击穿）→ 随机过期（防雪崩），四层防护形成闭环。但需要**验证布隆过滤器的初始化时机**——如果项目启动时 DB 为空但后续新增商品，布隆过滤器需同步更新。文档中 `addToBloomFilter` 方法已覆盖这一点。 |

---

#### 建议 5：分布式锁引入"锁粒度"和"读写锁"

> 锁粒度细化到 `skuId + 仓库ID`；读锁（RLock.readLock()）查询，写锁（RLock.writeLock()）扣减

| 评估维度 | 结论 |
|:---------|:-----|
| **是否合理** | ⚠️ 方向正确但**过度设计** |
| **文档是否已覆盖** | ❌ 未覆盖读写锁；锁粒度目前是 `lock:order:{userId}`（用户级） |
| **实施优先级** | P2（进阶优化，非必修） |

**详细分析**：

1. **锁粒度细化**：✅ 合理。当前 `lock:order:{userId}` 是"同一用户同一时刻只能下一个订单"，对于课程项目是够用的。SKU 级锁在于**不同用户抢购同一个 SKU**时互斥，这是真正的并发热点。建议**同时保留两个粒度**：用户级锁防重复下单，SKU 级锁防超卖。

2. **读写锁**：⚠️ 不建议引入。原因：
   - Redisson 读写锁基于 Redis Hash 实现，性能开销比普通锁大
   - 库存查询的场景**可以直接读 Redis 缓存**，无需加锁
   - 只有"写操作（扣减）"才需要互斥，**直接用单写锁即可**
   - 引入读写锁增加代码复杂度，答辩时也容易被追问"你测过读写锁比互斥锁吞吐量高多少吗？"

**推荐方案**：下单时 Redis Lua 脚本已经是**天然的无锁原子操作**（Redis 单线程执行脚本），优于分布式锁。保留 Lua 脚本方案 + SKU 级 Redisson 锁作为**双保险兜底（在 MySQL 层面防止超卖）** 即可。

#### 建议 6：乐观锁版本号双重校验

> 下单 SQL 加上 `update stock set amount = amount - 1 where sku_id = ? and version = ?`

| 评估维度 | 结论 |
|:---------|:-----|
| **是否合理** | ✅ **合理且必要** |
| **文档是否已覆盖** | ✅ **已覆盖**。`product_sku` 表有 `version` 字段 + `@Version` 注解；Lua 脚本注释中提及版本号参数 |
| **实施优先级** | 已设计，核对实现即可 |
| **点评** | 乐观锁是数据库层面的最后防线，即使 Redis Lua 脚本失败/失效，MySQL 也能兜底。需要确认 **MyBatis-Plus 的 @Version 是否在更新 product_sku 的 SQL 中生效**——如果库存扣减是通过手写 SQL 而非 MyBatis-Plus 的 `updateById`，则 `@Version` 不会自动生效，需要手动写 WHERE version = ? 条件。 |

#### 建议 8：全链路日志追踪（TraceId + MDC）

> 网关/拦截器生成 TraceId（UUID），通过 MDC 在所有日志中强制打印

| 评估维度 | 结论 |
|:---------|:-----|
| **是否合理** | ✅ **性价比极高的广度加分项** |
| **文档是否已覆盖** | ❌ 未覆盖。AOP 日志切面只记录了方法名/参数/IP/耗时，没有 TraceId |
| **实施优先级** | P0（强烈建议加入） |
| **实施难度** | 低（约 1~2 小时） |

**具体建议**：

```java
// 在 Gateway 的 GlobalFilter 中
String traceId = request.getHeaders().getFirst("X-Trace-Id");
if (traceId == null) traceId = UUID.randomUUID().toString().replace("-", "");
MDC.put("traceId", traceId);

// logback-spring.xml 日志格式
<pattern>%d{HH:mm:ss.SSS} [%thread] [%X{traceId}] %-5level %logger{36} - %msg%n</pattern>
```

价值：**一条 TraceId 就能串联"Gateway → Controller → Service → Redis → MySQL → MQ 消费者"的完整调用链**。即使没有引入 SkyWalking/ELK，也能体现你对分布式链路追踪底层原理的理解。

## 三、我的补充优化建议

基于对全部文档和代码的全面分析，从需求、深度、广度三个维度提出以下补充建议。

### 3.1 需求层面补充

#### 补 1：缺少"秒杀场景"设计

当前项目介绍中有"Sentinel 限流""Redis 分布式锁""MQ 削峰填谷"等秒杀相关技术，但**业务需求中没有明确的秒杀场景**。建议增加：

```
秒杀模块（独立于普通下单）：
1. 秒杀商品表（seckill_product）：活动时间、秒杀价格、限量库存
2. 秒杀流程：
   (a) 活动开始前 → Redis 预热库存，前端显示倒计时
   (b) 活动开始 → 用户点击"立即抢购"→ 请求先经过 Sentinel QPS 限流
                  → 再检测 Redis 布隆过滤器（过滤已下单用户）
                  → Redis Lua 原子扣减库存
                  → MQ 异步生成订单
   (c) 返回"抢购成功/失败"（不等待订单生成，异步化提升吞吐）
```

**价值**：秒杀是高并发电商系统的**MVP 场景**，能在答辩中展示"限流→布隆→Lua→MQ→订单"的完整技术链条，比普通下单有说服力 10 倍。

#### 补 2：补全"购物车价格校验"——防止价格篡改

当前下单接口接受前端传来的 `price` 和 `totalAmount`，存在**价格篡改风险**。建议：下单时**以后端实时查询的价格为准**，不信任前端传来的价格参数：

```java
// 下单时从数据库重新查询
for (OrderItemRequest item : items) {
    ProductSku sku = skuMapper.selectById(item.getSkuId());
    item.setPrice(sku.getPrice());  // 强制覆盖为数据库价格
}
```

**价值**：虽然是小改动，但体现了对"业务安全"的考虑，面试中经常被问到。

#### 补 3：缺少"用户地址管理"

订单表有 `consignee/phone/address` 字段，但**没有地址管理模块**。建议增加一个简单的**收货地址 CRUD**（用户可以有多个地址，下单时选择），2 小时可完成。会让项目更完整。

### 3.2 技术深度补充

#### 补 4：缓存与数据库一致性——延迟双删 + MQ 重试

文档中提到了 Cache Aside Pattern（先更新 DB→删缓存），但这是**最基础**的方案。建议引入**延迟双删**：

```
步骤：
1. 删除缓存
2. 更新数据库
3. 休眠 500ms（略大于一次读请求的耗时）
4. 再次删除缓存

失败兜底：
如果第 4 步删除失败 → 发送 MQ 延迟消息 → 消费者重试删除
```

**价值**：延迟双删 + MQ 重试是面试中"如何保证缓存一致性"的标准答案，能让你在答辩中脱颖而出。

#### 补 5：Redis 库存预热 + 定时同步到 MySQL

当前文档中 Redis 和 MySQL 的库存同步方向比较模糊。建议明确：

```
1. 库存更新的公认"唯一入口"是 Redis Lua 脚本
2. 定时任务（每 5 秒）将 Redis 库存增量同步到 MySQL：
   - 收集 Redis 中 stock:sku:{id}:frozen 的变化量
   - 批量 UPDATE product_sku SET stock = ?, version = version + 1
3. 极端情况恢复：MySQL 库存作为"真实库存"兜底
```

这比"下单时同步扣 MySQL 库存"效率更高——将同步**批量异步化**。

#### 补 6：增加"JWT 黑名单"机制——解决无法强制登出问题

当前 JWT 无状态，用户登出后 Token 依然有效直到过期。这是一个**常见的安全问题**。建议：

```java
// 登出时
String token = request.getHeader("Authorization").substring(7);
long ttl = jwtTokenProvider.getRemainingTTL(token);
redisTemplate.opsForValue().set("blacklist:token:" + token, "1", ttl, TimeUnit.MILLISECONDS);

// JWT 过滤器校验时
if (redisTemplate.hasKey("blacklist:token:" + token)) {
    throw new BusinessException(401, "Token 已失效");
}
```

**价值**：低成本（10 分钟实现），但体现了安全意识的深度思考。

### 3.5 功能需求闭环补充（第二轮分析）

> 审视范围：当前项目用户"买完"之后——没有评价、没有回看订单、没有实时反馈。以下 4 项补充让功能形成完整闭环，且每项都与高并发技术主题强相关。

#### 补 12：WebSocket 实时推送（P0 — 强烈建议）

**现状**：两处关键场景在凑合用轮询 ——
- `phase-4` 秒杀订单消费者注释："通知用户订单已生成（可轮询 GET /api/orders/{orderNo}）"
- `phase-5` 秒杀前端注释："轮询倒计时 + 实时库存（WebSocket 更佳，简化用轮询）"

轮询的问题：每 1 秒 1 次 HTTP 请求 × 1000 在线用户 = 1000 QPS 无意义开销。

| 维度 | 分析 |
|:-----|:-----|
| **技术价值** | Spring WebSocket + Redis Pub/Sub 跨实例广播 → 经典"MQ异步化 → 实时推送"模式，高并发面试高频考点 |
| **实施要点** | (1) Gateway 升级为支持 WebSocket 代理；(2) order-service 订单生成完毕后发布到 Redis Pub/Sub；(3) WebSocket Handler 订阅频道并推送给对应用户 |
| **推送场景** | 秒杀订单生成通知、支付结果通知、退款结果通知、库存恢复通知 |
| **架构** | `MQ消费者→订单完成→Redis PUBLISH "order:{userId}" → WebSocket推送给该用户的前端` |
| **预估工时** | 3h（WebSocket 基础设施） |
| **演示价值** | 秒杀按钮点下 3 秒后弹窗"恭喜抢到！订单号：xxx，去支付"，比"排队中请轮询"高级 10 倍 |
| **依赖** | Redis Pub/Sub（无需新中间件）、Gateway 需配置 WebSocket 路由 |

#### 补 13：我的订单 + 个人中心（P0）

**现状**：用户端有商品列表/详情/购物车/下单，但**没有"我的订单"页面**。用户下完单后看不到订单状态、历史记录、退款入口。

| 维度 | 分析 |
|:-----|:-----|
| **技术价值** | 中等（标准 CRUD），但**业务闭环不可缺失**——没有它，用户"买完"就找不到了 |
| **实施要点** | (1) order-service 追加订单列表查询（分页+状态筛选）；(2) 确认收货接口（status 3→4）；(3) 取消订单入口；(4) 前端"我的订单"页面 |
| **关联** | WebSocket 推送点击 → 跳转我的订单详情页，形成实时交互闭环 |
| **页面结构** | `个人中心 → {我的订单(状态Tab:全部/待支付/已支付/已完成/已取消), 我的收藏, 我的评价}` |
| **预估工时** | 4h（后端 2h + 前端 2h） |

#### 补 14：商品评价/评分系统（P1）

**现状**：完全没有评价功能，用户"确认收货"后闭环断裂。

| 维度 | 分析 |
|:-----|:-----|
| **技术价值** | ⭐⭐⭐ **又一个缓存设计演练场景**——评价列表（高并发读）+ 评分统计（缓存一致性）+ 评价增量更新（MQ 异步刷新统计缓存） |
| **DB 设计** | `review` 表：id / product_id / sku_id / order_no / user_id / score(1~5) / content / images(JSON) / status(0待审核 1通过 2拒绝) / create_time |
| **缓存设计** | `product:reviews:{productId}:page:{N}` → 评价列表分页缓存，新增评价时删除所有分页缓存；`product:rating:{productId}` → 评分统计（平均分+各星级数量），MQ 异步刷新 |
| **权限** | 仅"已完成"订单（status=4）可评价；每个订单每件商品只能评价一次 |
| **前置** | 需要"确认收货"和"我的订单"页面（补 13），形成下单→支付→收货→评价完整链路 |
| **预估工时** | 4h |

#### 补 15：到货通知（P2）

**现状**：商品售罄后用户只能干等。

| 维度 | 分析 |
|:-----|:-----|
| **技术价值** | Redis Set + Pub/Sub 的实战应用，天然衔接 WebSocket 实时推送 |
| **实施要点** | (1) 商品详情页"到货通知我"按钮 → Redis `SADD notify:sku:{skuId} userId`；(2) 管理员补货 → `SSCAN` 获取订阅用户 → `PUBLISH notify:user:{userId} "商品已到货"` → WebSocket 推送到各用户浏览器 |
| **预估工时** | 2h |
| **依赖** | 需要先有 WebSocket 基础设施（补 12） |

## 五、对原有建议的总体评价

原有建议中：

- **100% 方向正确**：10 条建议中有 7 条与项目文档已有设计**一致或高度吻合**，说明原建议者对高并发系统设计有较深理解
- **3 条存在偏差**：读写锁（过度设计）、MinIO（偏离核心主题）、Nacos 热刷新（演示场景不够直观）
- **最大缺失**：缺少**秒杀场景**——这是高并发电商的 MVP 演示场景，秒杀能将"Sentinel + 布隆 + Lua + MQ + 状态机"串联为一个完整故事线
- **最大遗漏**：前端只有管理后台没有用户端——答辩时评委看到用户端页面会加分很多

## 六、实施建议

1. **先补 P0，再补 P1**：在正式写业务代码前，先把 SKU 设计、预占实扣、TraceId、异常码这些**地基级别**的决策敲定
2. **秒杀场景强烈建议加入**：它能让分散的技术点（Redis/MQ/Sentinel）形成一条完整的**故事线**，答辩时从秒杀开始讲，评委能一次性看到所有技术价值
3. **用户端页面**虽然工时 8 小时，但产出物（可操作的用户界面）在答辩中比 PPT 更有说服力
4. **MinIO 和读写锁建议舍弃**：在 6 周时间约束下，把精力集中在"高并发性能优化"这个核心命题上，广度服务于深度
