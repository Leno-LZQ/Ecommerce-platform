## 7.2 高频面试问题 + 标准回答

### Q1：你们的缓存和数据库如何保证一致性？

```
A：采用 Cache Aside Pattern（旁路缓存模式）。
   - 读：先查缓存，缓存未命中则查数据库，将结果写入缓存
   - 写：先更新数据库，再删除缓存（而非更新缓存）
   
   极端情况处理：数据库更新成功但缓存删除失败 →
   通过 MQ 异步重试删除（延迟双删策略），
   保证最终一致性。
```

### Q2：RabbitMQ 如何保证消息不丢失？

```
A：从生产到消费的三段保障：
   1. 生产者 → Broker：Confirm 确认机制
      rabbitTemplate.setConfirmCallback() 监听确认
   2. Broker 持久化：队列和消息都设为 Durable
   3. Broker → 消费者：手动 ACK
      channel.basicAck() 处理成功后才删除消息
```

### Q3：Redis 分布式锁如果业务没执行完就过期了怎么办？

```
A：使用 Redisson 的"看门狗"机制。
   RLock.tryLock() → Redisson 自动启动一个定时任务，
   每 10 秒检查一次，如果锁还被当前线程持有，
   自动续期 30 秒。业务完成后 unlock 停止续期。
   
   对比：SETNX 需要手动设置过期时间，
   时间短了业务未完成锁就释放，时间长了死锁风险大。
```

### Q4：为什么不用 Seata 做分布式事务？

```
A：本项目的下单场景更适合 MQ 最终一致性：
   1. 高并发考虑：Seata AT 模式需要全局锁，性能开销大
   2. 选型考量：RabbitMQ 已经在项目中，无需引入额外组件
   3. 本项目写多读少，最终一致性（秒级延迟）完全可接受
   
   如果是金融转账场景（强一致性要求），会考虑 Seata TCC。
```

### Q5：你们系统能抗住多大并发？

```
A：单机单实例实测：
   - 商品详情（缓存）：QPS 3500+
   - 下单流程（含锁和事务）：QPS 100+
   - 整体并发用户：500 不宕机
   
   瓶颈分析：MySQL 连接数（默认 151）是主要瓶颈。
   改进方案：读写分离 + 分库分表 + 水平扩展服务实例。
```

### Q6：Redis 挂了怎么办？

```
A：多层降级策略：
   1. Redis 哨兵模式自动 Failover（主从切换）
   2. 缓存层不可用时：请求直接走数据库（业务降级）
   3. 热点数据预加载到本地缓存（Caffeine）作为最后防线
   4. 恢复后：通过日志重放重建 Redis 缓存
```

### Q7：秒杀系统怎么设计的？（新增）

```
A：四层防护，由外到内逐层过滤：
   1. Sentinel QPS 限流（100/s）→ 拦截 90% 请求，保护后端
   2. Redis 布隆过滤器 → 过滤已成功下单的用户（每人限购 1 件）
   3. Redis Lua 原子脚本 → 库存 -1 + 用户标记，< 1ms 完成
   4. MQ 异步生成订单 → 削峰填谷，用户立即收到"排队中"响应

   关键设计：
   - 库存预热：秒杀开始前将库存加载到 Redis，活动结束后同步 MySQL
   - 异步化：用户不等待订单生成，MQ 保证最终一致性
   - 无锁设计：Redis 单线程执行 Lua 脚本天然串行，优于分布式锁
```

### Q8：JWT 如何实现主动登出？（新增）

```
A：Token 加入 Redis 黑名单。
   - 登出时：redis.set("blacklist:token:" + token, "1", remainingTTL)
   - 校验时：JWT 过滤器检查 blacklist:token:{token} 是否存在
   - 内存友好：过期时间 = Token 剩余有效期，到期自动清除
   - 无需改 JWT 无状态模型，也不用引入 OAuth2/stateful session
```

### Q9：前端篡改价格怎么办？（新增）

```
A：永不信任前端传来的价格。下单时：
   1. 以 skuId 从数据库查询真实价格
   2. 强制覆盖前端传来的 price 字段
   3. 重新计算 totalAmount 并与前端比对（误差 > 0.01 元则拒绝）
   4. 最终以数据库价格为准生成订单

   这是电商系统最基本的业务安全设计，不依赖前端校验。
```

### Q10：WebSocket 如何保证消息不丢失？（新增）

```
A：三级保障：
   1. Redis Pub/Sub 自带连接重试（消息订阅者断线重连后自动恢复订阅）
   2. WebSocket 心跳机制：客户端每 30 秒 ping，服务端 pong 响应，超时则重建连接
   3. 兜底拉取：页面离线后重新上线，主动 GET /api/orders/my 拉取最新数据
   
   电商场景允许"最终通知"（秒级延迟），不需要 100% 实时送达
   （金融交易场景才会用 MQ 持久化 + 消费端 ACK 保证不丢）。
```

### Q11：评价系统如何提高查询性能？（新增）

```
A：三层缓存设计：
   1. 评价列表：product:reviews:{productId}:page:{N} → 分页缓存
      新增评价时删除该商品所有分页缓存（空间换一致性）
   2. 评分统计：product:rating:{productId} → Redis Hash 缓存
      新增评价后通过 MQ 异步刷新（最终一致性，延迟 < 5 秒）
   3. 热点商品评价 → 本地 Caffeine 缓存（防击穿）
   
   压测结果：评价列表缓存命中 TPS > 2000，评分统计 TPS > 5000。
```
