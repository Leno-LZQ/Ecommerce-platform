## 一、系统概述与设计目标

### 1.1 项目背景

本平台是一个面向多商户的 B2B2C 电商系统，支持平台自营与第三方商家入驻两种经营模式。系统需要同时服务三类用户角色：

| 端 | 用户群体 | 核心场景 |
|:---|:--------|:--------|
| **C 端（消费者）** | 普通买家 | 浏览商品、搜索、加购、下单、支付、查看订单与店铺、**咨询商家（消息）**、**联系官方客服（工单）**、**获取个性化推荐** |
| **B 端（商家）** | 入驻商户 | 商品管理、订单处理、店铺管理、账单核对、数据看板、**回复用户咨询（消息）** |
| **管理端（平台）** | 运营管理员 | 商家审核、商品审核、抽佣规则配置、结算打款、平台数据看板、**客服工单处理（分配/转接/解决）**、**推荐策略配置** |

### 1.2 设计目标

本系统从"课程/演示项目"出发，向"生产级系统"全面升级。设计目标覆盖功能性与非功能性两个层面：

#### 1.2.1 功能性目标

| 目标 | 说明 |
|:-----|:-----|
| **多商户平台化** | 支持商家入驻、审核、店铺管理、商品发布、订单处理、账单结算的完整 B 端生命周期 |
| **商品目录管理** | SPU/SKU 模型、多级分类、评价系统、到货通知 |
| **核心交易链路** | 购物车 → 下单 → 库存预扣 → 优惠计算 → 支付 → 订单完成，全链路闭环 |
| **买卖沟通** | 用户与商家之间的实时消息对话，支持文本/图片/商品卡片/订单卡片，WebSocket 长连接推送，离线消息不丢 |
| **官方客服** | 工单式客服体系，支持用户提交工单、客服分配/转接/解决，SLA 时效告警，纠纷处理全链路可追溯 |
| **智能推荐** | 基于协同过滤 + 热门排行 + 关联规则的多策略推荐引擎，覆盖"猜你喜欢""看了又看""买了还买"等场景，支持行为采集、离线计算、在线融合排序 |
| **全文搜索** | 基于 Elasticsearch 的商品搜索，IK 中文分词，聚合筛选 |
| **营销能力** | 独立促销引擎（promotion-service），支持优惠券（满减/折扣/无门槛）、满减满折活动（单/多阶梯）、限时秒杀、新人专享、N元M件等 8 种优惠类型，具备叠加/互斥规则引擎、预算管控、并发锁券、自动发券等完整营销链路 |
| **平台运营** | 数据看板（商家排行、订单趋势、类目分布、客服工单统计）、审核工作流 |

#### 1.2.2 非功能性目标

| 维度 | 目标 | 衡量指标 |
|:-----|:-----|:--------|
| **高可用** | 核心交易链路 99.9% 可用 | 年停机时间 < 8.76 小时 |
| **高性能** | 商品详情页 P99 < 200ms，下单 P99 < 500ms，推荐接口 P99 < 100ms | 日常 QPS ≥ 2000 |
| **高并发** | 秒杀场景 5000+ 并发，优惠锁券 Lua 原子 < 10ms，WebSocket 并发连接 5000+ | Redis 原子扣减 + 券并发 CAS |
| **数据一致性** | 库存强一致、订单/支付最终一致、消息不丢不重 | 零超卖，支付/订单秒级同步 |
| **安全合规** | 支付数据 PCI DSS 级别隔离，消息/客服数据隐私隔离，推荐数据匿名化 | 独立 Schema + 独立密钥 + 审计日志 |
| **可扩展** | 各服务独立水平扩容，推荐离线计算与在线服务解耦 | 按瓶颈点精准扩容，互不影响 |
| **可观测** | 3 分钟内定位线上故障 | Logs + Metrics + Traces 三维体系 |

### 1.3 设计原则

1. **Database per Service**：每个微服务拥有独立数据库/ Schema，严禁跨服务直接数据库访问
2. **异步解耦优先**：非关键路径上优先使用消息队列异步通信，降低同步耦合
3. **故障隔离**：单个服务故障不应级联影响核心交易链路，各服务配备降级策略
4. **宁可少卖，不可超卖**：库存服务不可用时拒绝下单，而非冒超卖风险
5. **读写分离（CQRS）**：高频读场景与低频写场景使用不同存储策略和通信模式
6. **安全纵深防御**：网络层 → 网关层 → 服务层 → 数据层 → 运维层五层防护
7. **优惠与交易分离**：优惠计算、规则匹配、券锁定量由独立的 promotion-service 负责，order-service 仅作为 Saga 编排器调用优惠结果，各司其职、互不侵入
8. **实时通信独立**：用户-商家消息、客服即时对话等长连接场景，基于 WebSocket 协议，由独立服务承载，避免阻塞 HTTP 业务链路
9. **推荐离线在线分离**：推荐模型计算（离线批处理）与推荐结果服务（在线 API）解耦，离线计算不占用在线资源，在线服务降级时回退到热门兜底

## 二、整体架构设计

### 2.1 架构风格

系统采用 **微服务架构**，基于 **Spring Cloud Alibaba** 技术栈，以 **领域驱动设计（DDD）** 的限界上下文作为服务划分依据。

```
架构风格选择理由：

✅ 微服务 vs 单体
   • 多团队并行开发：用户端、商家端、管理端由不同子团队负责
   • 独立扩容：库存（秒杀瓶颈）、搜索（高 QPS）需要独立扩缩容
   • 技术异构：搜索使用 ES、购物车使用 Redis-first 存储范式
   • 故障隔离：支付/库存故障不拖垮商品浏览

✅ Spring Cloud Alibaba vs 其他
   • Nacos：同时承担注册中心 + 配置中心，减少组件数量
   • Sentinel：与 Spring Cloud Gateway 深度集成，限流熔断开箱即用
   • 国内生态成熟，社区活跃，适合生产级部署
```

## 三、微服务划分与职责定义

### 3.1 服务全景清单

系统共包含 **15 个运行时单元**，服务划分基于 DDD 限界上下文分析，每个服务具有独立的业务价值、存储范式和安全边界。

| # | 服务 | 端口 | 数据库/Schema | 限界上下文 | 核心职责 |
|:--:|:-----|:---:|:------------|:---------|:--------|
| 1 | **gateway** | 8080 | 无 | API Gateway | JWT 鉴权、路由转发、全局限流、CORS、WebSocket 代理 |
| 2 | **user-service** | 8081 | ecommerce_user | Identity & Access | 注册登录、JWT 签发、RBAC 权限、地址管理 |
| 3 | **product-service** | 8082 | ecommerce_product | Product Catalog | 商品 SPU/SKU CRUD、分类管理、评价、审核 |
| 4 | **inventory-service** | 8083 | Redis + MySQL | Inventory | Redis Lua 原子库存扣减、预占/实扣/释放 |
| 5 | **cart-service** | 8084 | Redis（主）+ MySQL（灾备） | Shopping Cart | CQRS 购物车、商品快照、大 Key 分桶 |
| 6 | **order-service** | 8085 | ecommerce_order | Order Management | Saga 下单编排（含优惠锁定）、状态机、多商家订单拆分 |
| 7 | **payment-service** | 8086 | ecommerce_payment | Payment Processing | 支付单管理、回调处理、退款、审计日志 |
| 8 | **search-service** | 8087 | ES 独立集群 | Product Search | IK 分词搜索、聚合筛选、ES 索引管理 |

| `/ws/cs/**` | cs-service | ✅ (query token) | — | 1000 连接 |

**WebSocket 路由机制**：

#### 3.2.4 inventory-service（库存服务）

| 属性 | 说明 |
|:-----|:-----|
| **数据库** | Redis 主存储（实时库存）+ MySQL 持久层 |
| **定位** | 系统最关键的可扩展点，秒杀期间需独立 10 倍扩容 |

**核心操作**：

| 操作 | API | 实现 |
|:-----|:---|:-----|
| **查询库存** | `GET /api/inventory/{skuId}` | Redis 直接读取 |
| **预扣库存** | `POST /internal/inventory/reserve` | Redis Lua 原子操作：检查 → 扣减 |
| **确认扣减** | `POST /internal/inventory/confirm` | 预扣 → 实扣（订单支付成功后） |
| **释放库存** | `POST /internal/inventory/release` | INCR 回补（订单取消/超时） |
| **回滚库存** | `POST /internal/inventory/rollback` | INCR 回补（退款场景） |

**Lua 原子扣减脚本**：
```lua
-- reserve_stock.lua
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock == nil then
    return -1  -- key 不存在
end
if stock >= tonumber(ARGV[1]) then
    redis.call('DECRBY', KEYS[1], ARGV[1])
    return 1   -- 预扣成功
else
    return 0   -- 库存不足
end
```

**库存生命周期**：
```
商品创建 → 库存初始化 → 下单 → RESERVE(预扣) → 支付成功 → CONFIRM(实扣)
                                        └→ 超时/取消 → RELEASE(释放)
                        └→ 退款 → ROLLBACK(回滚)
```

**稳定性保障**：
- Redis AOF 持久化（appendfsync everysec）+ 每 5 分钟 MySQL 同步双保险
- 服务不可用时：**拒绝下单，宁可少卖、不可超卖**
- 秒杀期间独立扩容至 N 实例，Redis key 分散到不同 slot

#### 3.2.5 cart-service（购物车服务）

| 属性 | 说明 |
|:-----|:-----|

**CQRS 读写分离模式**：

```
写路径（加购时）：
  POST /api/cart {skuId, quantity}

读路径（查看购物车）：
  GET /api/cart
    → HGETALL cart:user:{userId}
    → 直接从 Redis 返回完整数据
    → 零跨服务调用

优惠预览路径（用户查看购物车时）：
  GET /api/cart（前端并行请求）

**Redis 数据结构**：
```
Key:   cart:user:{userId}   (Hash, TTL 30天)
Field: sku:{skuId}
Value: {"skuId":10001, "productName":"iPhone 15", "price":5999,
        "image":"xxx.jpg", "quantity":2, "checked":true,
        "snapshotTime":"2026-07-13T14:30:00"}

#### 3.2.6 order-service（订单服务）

| 属性 | 说明 |
|:-----|:-----|
| **数据库** | ecommerce_order（4 张表） |
| **拥有表** | orders, order_item, order_split, order_message |
| **定位** | 交易核心聚合根 + Saga 编排器 |

**Saga 下单编排流程**：

```
Step 1: 创建订单（status=CREATING）
    │
    ├─[成功]─→ Step 2: Feign → inventory 预扣库存（Redis Lua 原子操作）
    │              │
    │              ├─[成功]─→ Step 2.5: Feign → promotion 锁定优惠（券状态 0→1 + 活动预算预扣）
    │              │
    │              ├─[成功]─→ Step 3: Feign → payment 创建支付单
    │              │              │
    │              │              ├─[成功]─→ Step 4: 更新订单→PAID，发延迟消息(30min)
    │              │              │          ✅ 下单成功
    │              │              │
    │              │              └─[失败]─→ 补偿 Step 2.5: Feign promotion 释放券+预算
    │              │                         └→ 补偿 Step 2: Feign inventory 释放库存
    │              │                         🟡 已补偿
    │              │
    │              └─[失败]─→ 补偿 Step 2: Feign inventory 释放库存
    │                         🟡 已补偿
    │
    └─[失败]─→ 直接返回失败，CREATING 状态由延迟任务清理
```

**订单状态机**：

```
父订单：CREATED → PAID → COMPLETED
           │        │
           └── CANCELLED

子订单：CREATED → PAID → SHIPPED → RECEIVED → COMPLETED
           │        │        │
           └── CANCELLED    └── REFUNDING → REFUNDED

联动规则：
  • 所有子订单完成 → 父订单完成
  • 任一子订单取消且其他都取消 → 父订单取消
```

**多商家订单拆分**：
用户下单含商家 A + B 的商品 → order-service 按 merchantId 分组 → 原子生成子订单 → 写入 order_split 表。商家各自只能看到和处理自己的子订单。

**核心保障**：
- **幂等性**：Redis Token（UUID） + 数据库唯一索引 `uk_order_no`
- **超时取消**：RabbitMQ TTL(30min) + DLX 延迟队列
- **可靠消息**：本地消息表 order_message + 定时补偿
- **优惠回滚**：下单失败/超时取消自动调用 promotion.release 解锁券（status 1→0）+ 退还活动预算；定时任务每 5 分钟 scan Redis 超时 15min 的锁定券自动释放

#### 3.2.10 settlement-service（结算服务）

| 属性 | 说明 |
|:-----|:-----|
| **数据库** | ecommerce_settlement（独立 Schema，金融数据隔离） |
| **拥有表** | commission_rule, settlement_bill, settlement_detail |

**为什么从 merchant-service 拆出？**

```
merchant-service                    settlement-service
───────────────                    ─────────────────
实时在线服务                         离线批处理服务
• 商家入驻（高频写）                  • 每天凌晨 2:00 定时任务
• 店铺信息查询（C 端高频读）          • 扫描全量已完成子订单
• 资质审核                           • 计算佣金 → 生成账单
^ 合并风险：批处理拖慢在线服务、       • 账单确认 → 打款处理
  金融数据无法独立审计                • 金融数据独立审计
```

**定时结算流程**（每天凌晨 2:00）：
```
Step 1: 扫描已完成未结算的子订单
Step 2: 按 merchantId 分组
Step 3: 逐笔计算佣金（(subOrderAmount - discountAmount) × commissionRate）
Step 4: 插入 settlement_detail（记录计算时的佣金率快照）
Step 5: 汇总 → 插入 settlement_bill
Step 6: 更新 order_split.settlement_status
Step 7: 发布 settlement.bill.created → merchant 通知商家
```

**佣金规则匹配优先级**：
```
① categoryId 精确匹配 + merchantLevel 精确匹配
② categoryId 精确匹配 + merchantLevel=-1（分类默认）
③ categoryId=0 + merchantLevel=-1（全局默认）
```

**优惠对结算的影响**：
```
结算金额 = 子订单合计 - discount_amount - 佣金

优惠金额（discount_amount）在下单阶段已由 order-service 通过
promotion.lock 的结果写入 order_split.discount_amount 快照字段，
settlement-service 无需直接调用 promotion，只需读取该快照。

费用承担规则：
  • platform 发行的优惠券/活动 → 平台承担优惠费用
  • merchant 发行的优惠券/活动 → 对应商家承担优惠费用
  → 具体由 promotion_activity.issuer_type / coupon_template.issuer_type 决定
  → settlement 不做二次判断，仅按 discount_amount 扣除结算金额

退款场景：
  • 消费 promotion.coupon.refunded 事件 → 按退款比例回退结算金额
```

#### 3.2.12 promotion-service（优惠策略引擎）

| 属性 | 说明 |
|:-----|:-----|
| **数据库** | ecommerce_promotion（独立 Schema，8 张表） |
| **拥有表** | coupon_template, coupon_user, order_coupon, promotion_activity, promotion_rule, promotion_scope, seckill_activity, user_coupon_tag |
| **定位** | 独立促销引擎，负责优惠规则的配置、匹配、计算、锁定与核销全生命周期 |

**核心理念：优惠与交易分离**

promotion-service 遵循"优惠规则与交易流程分离"的设计原则，将优惠计算逻辑从 order-service 中抽离为独立的领域服务：

```
promotion-service 负责：
  ✅ 优惠规则的配置、校验、匹配
  ✅ 用户领券 / 自动发券（新人、等级触发）
  ✅ 下单时优惠金额的实时计算（DiscountEngine 五层计算）
  ✅ 优惠券/活动名额的 Redis 原子锁定（并发防超发）
  ✅ 支付后最终核销 + 取消/退款后退还

promotion-service 不负责：
  ❌ 订单的创建和状态变更（由 order-service 主导）
  ❌ 支付流程（由 payment-service 负责）
  ❌ 最终实付金额的写入（order-service 调用 promotion 拿到结果后自行存储到订单快照）
```

| 5 | **满折活动** | 平台/商家 | 满3件打8折 | promotion_activity 阶梯规则 |

**DiscountEngine 五层计算架构**：

下单时 promotion.lock 调用 DiscountEngine.calculate() 按以下五层模型依次执行：

```
Layer 1: 秒杀价替换
  ├── 检查每个 skuId 是否命中进行中的秒杀
  ├── 命中 → sku.price = seckillPrice
  └── 被秒杀价替换的商品标记 excludeFromOtherPromo=true（不参与后续优惠）

Layer 2: 促销活动匹配（满减/满折/N元M件）
  ├── 按 merchantId 对非秒杀商品分组
  ├── 每组匹配 promotion_activity + promotion_scope → 遍历 promotion_rule 阶梯
  ├── 多阶梯时取满足条件的最大优惠值
  └── 不同商家分组之间优惠独立

Layer 3: 优惠券匹配
  ├── 校验每张券：门槛 / 适用范围 / 有效期 / 互斥状态
  ├── 平台券：作用于全场，按金额比例分摊到各 order_item
  └── 商家券：仅作用于该商家的商品

Layer 4: 叠加与互斥判定
  ├── 优先级：秒杀 > 活动 > 优惠券
  ├── 满减活动 + 优惠券：允许叠加（活动后金额仍满足券门槛则可用券）
  ├── 多张平台券：互斥，只使用最优一张
  ├── 平台券 + 商家券：允许叠加，平台券先计算
  └── 折扣券优先级 > 满减券 > 无门槛券（同类型取抵扣最多的）

Layer 5: 优惠金额分摊
  ├── 按 order_item.subtotal 比例分摊优惠总额（精度到分，差额归最后一行）
  ├── 汇总 order_split.discount_amount（影响结算金额）
  └── 分摊结果写入 orders / order_item / order_split 的 discount_amount 字段
```

**优惠叠加与互斥规则矩阵**：

| 优惠 A | 优惠 B | 能否叠加 | 计算顺序 | 说明 |
|:------|:------|:------:|:------:|:-----|
| 秒杀价 | 满减活动 | ❌ | — | 秒杀是独立价格体系 |
| 秒杀价 | 优惠券 | ❌ | — | 秒杀商品不可用券 |
| 满减活动(A商家) | 满减活动(B商家) | ✅ | — | 不同商家活动独立 |
| 满减活动 | 平台优惠券 | ✅ | 先活动后券 | 打折后金额仍满足门槛则可用券 |
| 满折活动 | 平台优惠券 | ✅ | 先满折后券 | 满折后金额作为券门槛计算基数 |
| 满减活动 | 满折活动 | ❌ | — | 同商家同商品只选一种 |
| 平台券 A | 平台券 B | ❌ | — | 多张平台券互斥，只选最优 |
| 平台券 | 商家券 | ✅ | 先平台后商家 | 平台券减免后商家券作用于剩余金额 |
| N元M件 | 其他活动/券 | ❌ | — | N元M件是独立优惠模型 |

**Redis 原子锁定机制**：

```lua
-- lock_promotion.lua（在单次 Lua 脚本中原子执行）：
-- ① 校验券状态（必须为 0=未使用）
-- ② 校验活动预算充足性
-- ③ 校验用户每日参与次数
-- ④ 全部通过 → 券状态 0→1（已锁定，TTL 15min）+ 活动预算预扣
-- 任何一项失败 → 全部回滚，返回对应错误码
```

**防滥用策略**：

| 滥用场景 | 防护机制 | 实现层 |
|:--------|:--------|:------|
| 刷券 | user_limit 每人限领 + 同 IP 领券频次限制 | 业务层 + 网关 |
| 并发抢同一张券 | Redis Lua 原子 CAS（status 0→1） | 数据层 |
| 活动预算刷爆 | Redis Lua 原子预扣 + 预算不足直接拒绝 | 数据层 |
| 价格作弊（先涨后降） | 活动要求商品原价 30 天最低价校验 | 业务层 |
| 拆分订单逃券门槛 | 每张券仅限一个订单使用一次 | 业务层 |
| 退款套券 | 退还券状态=4（已退还），不可再次使用 | 业务层 |

**事件交互**：

- 消费 `user.registered` → 打标 NEW_USER + 自动发放新人券（有效期7天）
- 消费 `order.paid` → 券最终核销（status 1→2）+ 写入 order_coupon 快照
- 消费 `order.cancelled` → 释放已锁定的券和活动预算
- 消费 `order.refunded` → 按退款比例退还优惠券/活动预算
- 发布 `promotion.coupon.used` → settlement 接收优惠分摊结果通知
- 发布 `promotion.activity.budget.low` → admin 活动预算告警

#### 3.2.13 message-service（消息通信服务）

| 属性 | 说明 |
|:-----|:-----|
| **数据库** | ecommerce_message（独立 Schema，3 张表） |
| **拥有表** | conversation, message, push_record |
| **定位** | 用户与商家之间的实时消息对话中枢，承载售前咨询、订单沟通、售后协商等关键沟通链路 |

**核心理念：实时通信与业务解耦**

```
message-service 负责：
  ✅ WebSocket 长连接管理（用户端 + 商家端双通道）
  ✅ 会话生命周期管理（创建/归档/查询）
  ✅ 消息收发、持久化、离线推送
  ✅ 系统消息同步（订单状态通知推送到对话上下文）
  ✅ 商户隔离控制（用户与不同商家对话完全隔离）

message-service 不负责：
  ❌ 平台客服（由 cs-service 独立处理）
  ❌ 消息内容的业务语义解析（仅透传和存储）
  ❌ 推送通道的底层实现（对接第三方推送服务）
```

**WebSocket 连接模型**：

```
用户端 WebSocket：ws://gateway/ws/messages?token=xxx
  └── 每个用户一个 WebSocket 连接
  └── 连接建立后，message-service 维护 userId → WebSocketSession 映射
  └── 支持多 Tab 场景：同一用户多个连接，广播时遍历所有连接

商家端 WebSocket：ws://gateway/ws/messages?token=xxx
  └── 每个商家一个 WebSocket 连接
  └── merchantId → Set<WebSocketSession> 映射
  └── 支持商家多客服子账号（P2）
```

**核心 API**：

| 分组 | API | 说明 |
|:-----|:---|:-----|
| **C 端 REST** | `GET /api/messages/conversations` | 我的会话列表（按最近消息时间排序） |
| | `GET /api/messages/conversations/{id}/messages` | 会话历史消息（分页，倒序） |
| | `POST /api/messages/conversations` | 发起新会话（附带 product_id / order_id 上下文） |
| **商家端 REST** | `GET /api/messages/merchant/conversations` | 商家的会话列表 |
| | `GET /api/messages/merchant/conversations/{id}/messages` | 商家视角会话历史 |
| **WebSocket 帧** | `{type:"MESSAGE", conversationId, content, messageType}` | 发送消息（TEXT/IMAGE/PRODUCT_CARD/ORDER_CARD） |
| | `{type:"READ_ACK", conversationId}` | 已读回执 |
| | `{type:"TYPING", conversationId, isTyping:bool}` | 正在输入状态 |

**事件交互**：
- 消费 `order.paid` → 在用户与对应商家之间自动创建会话（如尚未存在），并发送系统消息"订单已支付"
- 消费 `order.shipped` → 向会话发送系统消息"订单已发货"，含物流单号

**关键技术设计**：

| 设计点 | 方案 |
|:------|:-----|
| **WebSocket 会话管理** | Spring WebFlux + Reactive WebSocket，ConcurrentHashMap<userId, Set<WebSocketSession>> |
| **消息可靠性** | 发送方先落库 → 再推送 → 接收方在线时发送 ACK，离线时写入 push_record 待推送 |
| **离线推送** | push_record 表记录待推送消息，定时任务扫表对接第三方推送（APNs/FCM/微信模板消息） |
| **历史消息性能** | conversation_id + created_at 联合索引，消息归档策略：90 天后冷数据迁移至归档表 |
| **商户隔离** | 会话创建时校验 product/order 归属 merchant，商家只能查看自己参与的对话 |
| **附件管理** | 图片等附件前端直传 OSS，消息体仅存储 URL |

#### 3.2.14 cs-service（官方客服服务）

| 属性 | 说明 |
|:-----|:-----|
| **数据库** | ecommerce_customer_service（独立 Schema，4 张表） |
| **拥有表** | ticket, ticket_message, ticket_audit_log, cs_agent |
| **定位** | 平台官方客服工单系统，处理纠纷、申诉、投诉等需要平台介入的场景 |

**为什么与 message-service 拆开？**

```
message-service                      cs-service
───────────────                     ─────────────
点对点自由对话                        工单式有状态流转
• 用户 ↔ 商家双向                     • 用户 → 平台客服（多对多）
• 无 SLA 约束                        • 严格 SLA 时效管控
• 会话自动/手动归档                   • 工单状态机 + 审计日志
• 无需审核                           • 纠纷需平台取证
^ 合并风险：两套完全不同的业务模型
  强行合并会导致状态机混乱、安全边界模糊
```

**工单状态机**：

```
CREATED（用户提交）
   │
   ▼
ASSIGNED（系统/管理员分配客服）
   │
   ├──────────────→ IN_PROGRESS（客服处理中）
   │                      │
   │                      ├──→ RESOLVED（客服标记已解决）
   │                      │        │
   │                      │        ├──→ CLOSED（用户确认 / 超时自动关闭）
   │                      │        │
   │                      │        └──→ IN_PROGRESS（用户不满意重新打开）
   │                      │
   │                      └──→ ASSIGNED（转接其他客服）
```

**核心 API**：

| 分组 | API | 说明 |
|:-----|:---|:-----|
| **用户端 REST** | `POST /api/cs/tickets` | 创建工单（category + priority + 关联 order_id） |
| | `GET /api/cs/tickets` | 我的工单列表 |
| | `GET /api/cs/tickets/{id}` | 工单详情（含消息历史） |
| | `POST /api/cs/tickets/{id}/messages` | 发送消息 |
| | `POST /api/cs/tickets/{id}/resolve-confirm` | 确认解决 / 不满意重新打开 |
| **用户端 WebSocket** | `ws://gateway/ws/cs?token=xxx` | 客服消息实时推送 |
| **客服端 REST** | `GET /api/cs/agent/tickets` | 工单池（待分配 + 我的工单） |
| | `POST /api/cs/agent/tickets/{id}/assign` | 认领工单 |
| | `POST /api/cs/agent/tickets/{id}/transfer` | 转接工单 |
| | `POST /api/cs/agent/tickets/{id}/resolve` | 标记已解决 |
| **内部 Feign** | Feign ← order-service | 拉取关联订单详情 |
| | Feign ← payment-service | 拉取支付记录（退款纠纷） |
| | Feign ← merchant-service | 拉取商家信息（投诉工单） |
| | Feign ← message-service | 推送工单状态变更通知到用户消息列表 |

**客服智能分配策略**：

```
① 按工单 category 匹配 agent 专长领域
② 同领域内，选择当前负载最低的 agent（current_tickets < max_concurrent）
③ 无匹配领域 agent → 分配给 MANAGER 角色兜底
④ 15 分钟内未响应 → 自动升级到上级 agent
```

**SLA 时效管控**：

| 优先级 | 首次响应 SLA | 解决 SLA | 实现方式 |
|:-----:|:---------:|:------:|:--------|
| 🔴 高（纠纷/投诉） | 2h | 24h | Redis TTL 延迟队列：`cs:sla:{ticketId}` 到期触发告警 |
| 🟠 中（账号申诉/举报） | 4h | 48h | 同上 |
| 🟡 低（一般咨询） | 24h | 72h | 同上 |

**防滥用策略**：

| 滥用场景 | 防护机制 |
|:--------|:--------|
| 同一用户大量创建工单 | Redis 滑动窗口限流：5 个/小时 |
| 工单状态回退刷屏 | 用户对同一工单"不满意重新打开"每天最多 3 次 |
| 客服端敏感操作 | 转接/关闭工单需二次确认 + 写入 ticket_audit_log |
| 工单消息包含敏感信息 | 引导用户在 OSS 通道上传截图，避免正文中出现身份证/银行卡号 |

**事件交互**：
- 消费 `order.refunded` → 自动关闭相关纠纷工单
- 发布 `cs.ticket.created` → admin dashboard 工单统计
- 发布 `cs.ticket.overdue` → SLA 超时告警（钉钉 + 短信）
- 发布 `cs.ticket.resolved` → 通知用户"工单已处理"

│                                                                  │

│  └── 消费 MQ 行为事件 → Redis ZSet 用户最近行为更新              │
│                                                                  │
│  数据源：user_behavior + orders + product + search_keyword       │
└─────────────────────────────────────────────────────────────────┘
```

**推荐策略融合模型**：

```
用户请求推荐
    │
    ├── 召回路 1: 协同过滤（User-CF + Item-CF）→ 最多 50 候选
    ├── 召回路 2: 热门商品（销量+评分+浏览加权）→ 最多 30 候选
    ├── 召回路 3: 用户画像标签匹配（"科技数码爱好者"→3C 品类）→ 最多 30 候选
    ├── 召回路 4: 新人专享（冷启动策略）→ 新人专属商品
    └── 召回路 5: 搜索历史关联（最近搜索词相关商品）→ 最多 20 候选
    │
    ▼
融合排序：加权 score + 去重（同 SPU 只保留最高分 SKU）
         + 类目打散（每页同类不超过 3 个）
         + 过滤已购商品（Redis Set `reco:purchased:{userId}`）
         + 过滤差评商品（评分 < 3.0 不推荐）
    │
    ▼
返回 Top 20（含分页）
```

**用户行为采集清单**：

| 行为类型 | 采集点 | 权重 | MQ Topic | 说明 |
|:-------|:------|:---:|:--------|:-----|
| VIEW | 商品详情页加载 | 1 | `behavior.view` | 浏览行为，异步批量写入 |

**数据依赖（Feign 消费）**：

| 依赖服务 | 用途 | 超时 |
|:--------|:-----|:---:|

| **search-service** | 获取热搜关键词辅助画像 | 200ms |
| **user-service** | 获取用户注册时间（冷启动判断） | 100ms |

**事件交互**：
- 消费 `behavior.view/search/add_cart/purchase` → 写入 user_behavior 表 + 更新 Redis ZSet 用户行为缓存
- 消费 `order.paid` → 高权重购买行为记录 + 更新"已购"过滤集
- 消费 `product.created` → 加入新品池（新品加权探索）
- 消费 `product.status.changed` → 更新可推荐商品池
- 消费 `user.registered` → 创建新用户画像（触发冷启动策略）
- 发布 `recommendation.refreshed` → 可选通知前端（低频，T+1）

**关键技术设计**：

| 设计点 | 方案 |
|:------|:-----|
| **行为日志量** | 日均百万级，user_behavior 按 date 分区，30 天热数据 + 全量冷数据归档 |
| **冷启动** | 新用户：全局热门 + 新人专享商品 + 同注册时段热门；新商品：新品池加权 + 随机流量探索 |
| **实时推荐** | 离线计算 T+1 全量，准实时用 Redis ZSet 存最近 7 天行为（TTL 7d）做轻量在线调整 |
| **多样性** | 融合排序阶段 MMR（Maximal Marginal Relevance）打散同类目商品 |
| **负反馈** | 用户"不感兴趣"→ 写入 Redis Set `reco:exclude:{userId}` TTL 30 天 |
| **A/B 实验** | reco_strategy.config_json 存策略参数 + weight，按 userId hash % 100 分流 |
| **降级兜底** | 推荐服务不可用时，前端降级展示全局热门商品列表 |
| **计算规模** | 日均 10 万订单，协同过滤用 Java 定时任务即可；日千万订单量级需引入 Spark/Flink |

#### 3.3.4 实时通信规范（WebSocket）

```
协议栈：
  Nginx（Upgrade: websocket 代理）
    → Spring Cloud Gateway（WebSocket 路由）
      → message-service / cs-service（Spring WebFlux + Reactive WebSocket）

连接流程：
  ① 前端携带 JWT token 发起 ws://gateway/ws/messages?token=xxx
  ② Gateway 识别 /ws/** 路径，不拦截鉴权，直接代理到 message-service
  ③ message-service 解析 token，校验有效性，建立 WebSocketSession
  ④ 维护 userId/merchantId → Set<WebSocketSession> 映射

心跳与重连：
  • 前端心跳：每 30s 发送 PING 帧
  • 服务端超时：90s 无心跳 → 关闭连接，清理会话映射
  • 前端重连：指数退避（1s→2s→4s→...最大 30s）

消息可靠性：
  • 发送方先落库 MySQL → 再推送 WebSocket
  • 在线：直接推送 → 接收方回 ACK 帧
  • 离线：写入 push_record → 定时任务对接第三方推送
  • 未 ACK：定时重推（最多 3 次）
```

### 4.4 数据一致性策略

| 场景 | 涉及服务 | 一致性要求 | 方案 |
|:-----|:--------|:--------:|:-----|
| 下单 → 扣库存 | order → inventory | **强一致** | Saga 编排 + 补偿 |
| 下单 → 锁定优惠 | order → promotion | **强一致** | Saga 编排（Step 2.5）+ Redis Lua 原子锁 |
| 下单 → 创建支付单 | order → payment | **强一致** | Saga 编排 + 补偿 |
| 支付回调 → 更新订单 | payment → order | **最终一致** | MQ + 本地消息表 |
| 支付回调 → 券核销 | promotion → order | **最终一致** | MQ → order.paid → promotion.confirm |
| 支付回调 → 消息通知 | order → message | **最终一致** | MQ order.paid → message 发送系统消息 |
| 订单取消 → 解库存 | order → inventory | **最终一致** | MQ 异步 + 定时补偿 |
| 订单取消 → 退券 | order → promotion | **最终一致** | MQ order.cancelled → promotion.release + 定时 15min 自动释放 |
| 商品变更 → ES 更新 | product → search | **最终一致** | MQ 异步 |
| 商品变更 → 购物车快照 | product → cart | **最终一致** | MQ 异步 |

| 行为采集 → 推荐更新 | gateway → recommendation | **最终一致** | MQ 异步批量写入 + 准实时 Redis ZSet 更新 |

| 订单完成 → 触发结算 | order → settlement | **最终一致** | MQ 异步 + 定时任务 |

### 4.5 分布式事务方案

**Saga 编排模式**（下单核心链路）：
- order-service 作为 Saga 编排器，主导 4 步正向操作（创建订单 → 预扣库存 → 锁定优惠 → 创建支付单）
- 后续步骤失败时，**倒序执行补偿**（关闭支付单 → 释放优惠 → 释放库存 → 取消订单）
- 补偿失败 → 写入补偿失败表 → 人工介入 + 定时任务兜底

**本地消息表 + MQ**（非关键路径）：
```
① 本地事务：INSERT order + INSERT order_message（同一事务）
② 定时任务扫描 status=0 的消息 → 发送 MQ
③ 发送成功 → 更新 status=1，消费成功 → status=2
④ 重试超过阈值 → 告警人工介入
```

### 4.6 Redis 多实例策略

| Redis 实例 | 用途 | 数据结构 | 持久化 |
|:----------|:-----|:--------|:-----|
| **共享 Redis** | 分布式缓存、Session、限流计数、Token 黑名单、在线状态、推荐热缓存 | String/Set/ZSet | RDB + AOF |
| **inventory Redis** | 实时库存（Lua 原子操作） | String（计数器） | AOF everysec |
| **cart Redis** | 购物车（CQRS 读模型） | Hash（大 Key 分桶） | RDB 30min + MySQL 灾备 |
| **promotion Redis** | 券锁定状态、活动预算、用户日限计数器 | String（券状态/预算）+ Lua 原子脚本 | AOF everysec |

> **promotion Redis 关键设计**：券锁定采用 Redis String 存储状态（key=`coupon:status:{couponCode}`），下单时 Lua 脚本 CAS 原子操作 0→1（TTL 15min 防死锁）；活动预算实时计数器（key=`activity:budget:{activityId}`）；用户每日参与频次计数器（key=`activity:user:{id}:{userId}:{date}`，TTL 24h）。MySQL coupon_user 为真实数据源，Redis 为实时并发控制层。主从切换时锁数据丢失由 MySQL 兜底 + 定时任务自动过期释放。

**新增 Redis 用途（共享 Redis 内）**：

| Key 模式 | 用途 | 数据结构 | TTL |
|:--------|:-----|:--------|:--:|
| `ws:user:{userId}` | 用户 WebSocket 在线状态 | String（sessionId） | 绑定连接生命周期 |
| `ws:merchant:{merchantId}` | 商家 WebSocket 在线状态 | Set（sessionIds） | 绑定连接生命周期 |
| `reco:hot:{categoryId}` | 推荐热门商品缓存 | ZSet（productId + score） | 1h |
| `reco:user:{userId}:recent` | 用户最近行为缓存 | ZSet（productId + timestamp） | 7d |
| `reco:purchased:{userId}` | 已购商品过滤集 | Set（productId） | 永久 |
| `reco:exclude:{userId}` | 用户"不感兴趣"集合 | Set（productId） | 30d |
| `cs:sla:{ticketId}` | 客服工单 SLA 延迟队列 | String（到期 KeyEvent） | 按 SLA 等级 |
| `cs:user:limit:{userId}` | 用户创建工单频次限制 | String（计数器） | 1h |

### 5.2 认证授权流程

**双 Token 机制**：
| Token | 有效期 | 存储位置 | 用途 |
|:------|:-----:|:--------|:-----|
| **Access Token** | 15 分钟 | 客户端内存 | API 请求鉴权 |
| **Refresh Token** | 7 天 | HttpOnly Cookie | 刷新 Access Token |

**Refresh Token 轮换机制**：每次刷新后旧 RT 立即失效（Redis 记录），防止 RT 泄露后滥用。

**防暴力破解**：同一账号 5 次登录失败 → 15 分钟锁定（Redis TTL），注册接口同 IP 限频 5 次/分钟。

### 5.3 服务间认证

内部服务间调用使用 **HMAC-SHA256 签名**（非 JWT），由 Feign 拦截器自动注入：

```java
// 内部服务调用认证
String timestamp = String.valueOf(System.currentTimeMillis());
String signature = HmacUtils.hmacSha256(internalSecret,
    template.method() + template.url() + timestamp);
// 注入 Headers: X-Internal-Timestamp, X-Internal-Signature, X-Source-Service
```

### 5.5 优惠防滥用专项设计

优惠模块面临六大典型滥用场景，需要从业务层、网关层、数据层多层协同防御：

| 滥用场景 | 防护机制 | 实现层 |
|:--------|:--------|:------|
| **刷券**（同一用户大量领券） | ① user_limit 每人限领 ② 同 IP 领券频次限制（Redis 滑动窗口） ③ 单人持有未使用券上限 20 张 | 业务层 + 网关层 |
| **并发下单抢同一张券** | ① Redis Lua 原子 CAS（券状态 0→1）② 乐观锁 version | 数据层 |
| **活动预算被刷爆** | ① Redis Lua 原子预扣（预算不足直接拒绝）② 多阶梯取最大时仍需校验预算 | 数据层 |
| **价格作弊**（先涨后降参与活动） | ① 活动要求商品原价 30 天最低价校验 ② 商家端活动申报审核 | 业务层 |
| **拆分订单逃券门槛** | ① 每张券只能在一个订单中使用一次 ② 同一用户短时间多笔小订单限流 | 网关层 + 业务层 |
| **退款套券**（买后退券保留券） | ① 退款后退还的券状态=4（已退还），不可再次使用 ② 活动预算退还而非券复用 | 业务层 |
| **券码穷举攻击** | ① coupon_code 使用雪花算法（非递增、难枚举）② 券查询需 user_id + coupon_code 双重匹配 | 数据层 |

### 5.6 消息通信安全

| 安全维度 | 防护机制 |
|:--------|:--------|
| **会话隔离** | 用户-商家对话按 conversation_id 隔离；用户查询会话时校验 user_id 归属，商家查询时校验 merchant_id 归属 |
| **消息内容安全** | 图片/附件前端直传 OSS 签名 URL，message 表仅存 URL；消息列表 API 返回脱敏后的内容（过滤潜在XSS） |
| **WebSocket 鉴权** | WS 握手时 query 参数携带 JWT token，message-service 建立连接时校验；连接断开/过期自动清理 |
| **防止消息轰炸** | 同一用户对同一商家 1 分钟内最多 30 条消息（Redis 滑动窗口） |
| **消息不可否认性** | 消息记录全量持久化，包含 sender_type + sender_id + timestamp，纠纷时可作为举证材料 |

### 5.7 客服安全与合规

| 安全维度 | 防护机制 |
|:--------|:--------|
| **工单分配安全** | 只有 ADMIN 和 CS_MANAGER 角色可手动分配/转接工单，普通 AGENT 只能认领未分配的工单 |
| **敏感操作审计** | 所有工单状态变更（分配/转接/解决/关闭/重开）写入 ticket_audit_log，不可删除 |
| **用户隐私保护** | 客服查看用户信息时手机号自动脱敏，禁止客服对外泄露用户隐私数据 |
| **纠纷证据保全** | 工单关联的 order_id 可拉取订单快照；工单消息不可由单方删除，关闭的工单 180 天后归档 |

### 5.8 推荐隐私与合规

| 安全维度 | 防护机制 |
|:--------|:--------|
| **数据匿名化** | 行为日志存储时使用 user_id（内部 ID），不关联手机号/真实姓名；对外数据分析使用聚合匿名数据 |
| **用户控制权** | 用户可在设置中关闭个性化推荐（关闭后仅推送热门排行）；用户可请求删除 30 天内的行为记录 |
| **数据最小化** | 仅采集推荐所需的 6 种行为类型，不采集用户在其他页面的浏览行为；session_id 不关联用户账号 |

## 六、部署架构与运维方案

### 6.1 容器化策略

所有服务均通过 Docker 容器化部署，使用 Docker Compose 进行编排。核心配置原则：

| 配置项 | 策略 |
|:-------|:-----|
| **资源限制** | 每服务设置 memory limits（128M~512M），防止容器间资源争抢 |
| **重启策略** | `restart: unless-stopped`，异常退出 `max_attempts: 3` |
| **健康检查** | 所有服务配置 Docker healthcheck（interval 10s~15s，retries 3） |
| **网络隔离** | 统一 `ecommerce-net` 桥接网络，内部通信 |
| **卷挂载** | 中间件数据持久化到命名卷（mysql-data, redis-data 等） |
| **环境变量** | 敏感信息通过 `.env` 文件注入，不硬编码，Git 忽略 |

#### 7.3.2 Feign 降级模式

```java
@Component
public class InventoryFallbackFactory implements FallbackFactory<InventoryClient> {
    @Override
    public InventoryClient create(Throwable cause) {
        return request -> {
            log.error("库存服务降级: {}", cause.getMessage());
            // 降级策略：拒绝下单——宁可少卖，不可超卖
            return Result.error(ErrorCode.INVENTORY_SERVICE_UNAVAILABLE);
        };
    }
}
```

```java
// Promotion 降级：下单时优惠不可用 — 拒绝下单，宁可少优惠、不可坏账
@Component
public class PromotionFallbackFactory implements FallbackFactory<PromotionClient> {
    @Override
    public PromotionClient create(Throwable cause) {
        return request -> {
            log.error("优惠服务降级: {}", cause.getMessage());
            return Result.error(ErrorCode.PROMOTION_SERVICE_UNAVAILABLE,
                "优惠服务繁忙，下单请稍后重试");
        };
    }
}
```

#### 7.3.3 数据恢复机制

| 场景 | 恢复策略 |
|:-----|:--------|
| Redis 宕机 | AOF 恢复 + MySQL 定时同步数据回灌 |
| 消息丢失 | 本地消息表 + 定时补偿扫描 |
| Saga 补偿失败 | 写入补偿失败表 → 人工介入 + 自动重试 |
| ES 索引丢失 | 定时全量重建（凌晨）+ 手动触发 |
| 消息推送失败 | push_record 表定时重试（20s/1min/5min/30min 阶梯退避）→ 3 次后告警 |
| 推荐结果丢失 | 立即触发 offline compute 重建；降级为热门商品兜底 |
| 券锁定超时 | 定时任务每 5 分钟 scan Redis `coupon:status:*` 中 TTL 已过期的 key → 状态回退为 0 + MySQL 兜底校验 |
| 活动预算超支 | Redis 实时预算计数器 + 每 5 分钟 MySQL 同步；Redis 宕机期间拒绝所有优惠活动下单 |
| WebSocket 连接断连 | 前端自动重连（指数退避 1s→30s），重连后拉取离线期间未读消息 |
